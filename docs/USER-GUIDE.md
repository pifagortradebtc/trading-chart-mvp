## 1. Что это вообще

`Pifagor Portfolio Research` — **аналитическая площадка** Криптофонда. Она помогает ответить на единственный вопрос:

> «Какую композицию портфеля из 7-8 криптоактивов мы должны рекомендовать фонду на следующий период?»

Платформа **не торгует**, **не пишет в фонд напрямую** и **не имеет доступа к балансам инвесторов**. Это **research-инструмент**, который выдаёт JSON-композицию. Управляющий (оператор) **вручную** копирует JSON и подаёт его в админку Криптофонда. Это сознательное архитектурное решение: между research и production-фондом всегда стоит человек, чтобы баг в моделях не попал в реальные деньги.

```
┌─────────────────────────┐         ┌──────────────────┐         ┌─────────────────────┐
│  PORTFOLIO RESEARCH     │         │  ОПЕРАТОР        │         │  КРИПТОФОНД         │
│  trading-chart-mvp      │         │  (человек)       │         │  pifagor.fund       │
├─────────────────────────┤         ├──────────────────┤         ├─────────────────────┤
│  14 моделей             │         │  1. Проверяет    │         │  PUT /admin/        │
│  + Risk Caps            │ ─JSON→  │  2. Подтверждает │ ─PUT→   │  portfolio/         │
│  + CVaR-Defense         │         │  3. Копирует     │         │  composition        │
│  = Final Fund Portfolio │         │                  │         │  → инвесторам       │
└─────────────────────────┘         └──────────────────┘         └─────────────────────┘
                ↑                                                          │
                │                  Δ vs Live Fund (read-only)              │
                └──────────────────────────────────────────────────────────┘
```

## 2. Быстрый старт (5 минут)

1. Открой <https://trading-chart-mvp.onrender.com>.
2. Кликни **«Портфель»** в правом верхнем углу.
3. В разделе **«Активы»** убедись, что выбраны: `BTC, ETH, SOL, BNB, HYPE, TON, OKB` (MNT добавь, если фонд начинает в него инвестировать).
4. **Период истории** — `2 года` (рекомендуемый default для текущего universe; на 3+ года HYPE выпадает в watchlist из-за короткой истории).
5. **Симуляций** — `50 000` (баланс точности и скорости).
6. Нажми **«Пересчитать»**. Ждать 5-15 секунд.
7. Перейди на вкладку **«Recommended»**.
8. Просмотри блоки сверху вниз: Confidence → Why narrative → донат-диаграммы → Cluster Exposure → Δ vs Live Fund → Rebalance Plan.
9. Если всё ок — нажми **«Copy NAV»** в шапке. JSON в буфере.
10. Открой админку фонда (`pifagor.fund/admin`) → Composition → вставь JSON → Submit.
11. Вернись в research → вкладка **«Journal»** → убедись, что свежий run записан с пометкой **published**.

Это типичный цикл ребаланса. Подробности — ниже.

## 3. Шапка управления — параметры расчёта

Над вкладками — три блока ввода, которыми ты задаёшь **что считать**.

### 3.1 Активы

Кликабельные чипы (BTC, ETH, …) — это **universe фонда**. Поле `BTC или BTCUSDT` принимает ручной ввод нового тикера. **«Быстрый выбор»** — список одобренных активов (MNT, XRP, и др.).

**Важно**: не каждый тикер автоматически работает. У нас есть три источника данных:

| Тикер | Источник | Глубина истории |
|---|---|---|
| BTC, ETH, SOL, BNB, TON, MNT | Binance Spot | 3-10+ лет |
| OKB | OKX | ~7 лет |
| HYPE | CoinGecko | ~17 месяцев (capped 365 дней на free tier) |
| Остальные | Binance Spot (если пара существует) | зависит от тикера |

Если добавишь новый тикер, который Binance не торгует (например, любой токен с DEX), будет warning «Не удалось загрузить котировки».

### 3.2 Период истории

`1 год / 2 года / 3 года / 5 лет` — на каком окне обучать модели.

- **Короткое окно (1-2 года)**: точнее отражает текущий режим рынка. Подходит для свежих листингов (HYPE).
- **Длинное окно (3-5 лет)**: включает медвежью фазу 2021-2022, статистика устойчивее, но HYPE автоматически попадает в watchlist (нет такой истории).
- **Рекомендация**: для текущего universe — **2 года**. Это компромисс: HYPE участвует, но окно достаточно длинное для устойчивых ковариаций.

### 3.3 Симуляций

`10k / 25k / 50k / 100k` — количество Monte-Carlo точек для Simulation tab.

- Больше точек = точнее Efficient Frontier, но медленнее.
- **50k** — оптимум для 7-8 активов.
- 100k имеет смысл при universe >10 активов.

### 3.4 Безрисковая ставка

Слайдер `0-10%`. Используется в формуле Sharpe = (return − rf) / vol. Текущий default — **4.0%** (примерный US Treasury 10Y).

### 3.5 Ограничения долей

Сворачиваемая секция. Здесь живут **per-asset bounds** для **Monte-Carlo симуляции** (не путать с Risk Caps в вкладке Risk Caps & Views — те для финальной композиции). Обычно не трогают.

## 4. Шесть вкладок — детальный разбор

После **«Пересчитать»** становятся доступны шесть вкладок. Они идут в **порядке аналитического процесса**: от широкого пространства возможностей до конкретного решения.

### 4.1 Simulation — пространство возможностей

**Что это**: Monte-Carlo Efficient Frontier по теории Марковица.

**Что видно на экране**:

- **Облако из 50 000 точек.** Каждая точка — один портфель со случайными весами.
- **Ось X** (волатильность) — какой риск.
- **Ось Y** (доходность) — какая отдача.
- **Цвет точки** — Sharpe ratio (синий → фиолетовый).
- **Зелёная кривая** — Efficient Frontier. Это **граница Pareto-оптимальных портфелей**: для каждого уровня риска — максимально возможная доходность.
- **Три именные точки**: Min Volatility (минимум риска), Max Sharpe (лучшее return-на-риск), Max Sortino (то же, но штрафует только downside).

**Когда смотреть**:

- В **самом начале анализа** — чтобы понять, какой ландшафт возможностей у universe.
- При **смене universe** (добавили / убрали актив) — проверить, не сломалась ли frontier.
- **Sanity check**: если три именные точки лежат под зелёной кривой — что-то не так с математикой (никогда не должно).

**Польза**:

- Видишь сразу, что «случайный портфель» (любая точка в облаке) почти всегда хуже оптимизированных. Это доказательство, что **оптимизация имеет смысл**.
- Понимаешь, насколько крута frontier — крутая = большой trade-off между риском и доходностью, плоская = разница невелика.
- Видишь, как изменения параметров (период, бесрисковая ставка) сдвигают frontier.

**Что НЕ делать**: не использовать Max Sharpe напрямую как руководство к действию. Это «наивная» MVO — она часто концентрирует портфель в одном активе и переоптимизируется под исторический шум.

### 4.2 Strategies — 14 моделей построения портфеля

**Что это**: 14 разных алгоритмов решают «как распределить капитал», каждый по-своему. Результаты показаны как **карточки** сверху и **сравнительная таблица** снизу.

#### 4.2.1 Карточки моделей

Каждая карточка содержит:

- **Название модели** + ID (например, `MAXSHARPE`).
- **Главная метрика** в правом верхнем углу (например, `0.653` для Max Sharpe — это значение Sharpe).
- **Три полоски**: Return / Vol / Max DD — реализованные характеристики этой раскладки на бэктесте.
- **Раскладка по активам**: тикеры с весом ≥ 1%, отсортированные по убыванию.

#### 4.2.2 Карта 14 моделей

| Модель | Идея в одно предложение |
|---|---|
| **Market Cap** | Пропорционально капитализации — пассивный equilibrium |
| **Equal Weight** | Поровну — наивный, но устойчивый бенчмарк |
| **Min Volatility** | Минимум скачков, не учитывая доходность |
| **Max Sharpe** | Лучшее «вознаграждение за единицу риска» |
| **Max Sortino** | То же, но штрафует только нисходящую волатильность |
| **Risk Parity** | Каждый актив несёт равный риск-вклад (inverse-vol) |
| **Black-Litterman** | Equilibrium + твои views на доходность |
| **CVaR-Optimal** | Минимизация худшего хвоста (CVaR-95) |
| **HRP** | López de Prado: кластеризация по корреляции, robust к шуму |
| **Max Diversification** | Максимум diversification ratio (Choueifaty & Coignard) |
| **Momentum** | Веса пропорциональны 200-дневному моментуму |
| **Fractional Kelly** | Half-Kelly haircut — оптимум long-term growth, осторожный |
| **Resampled Markowitz** | Усреднение MVO по 19 200 bootstrap-resamples (Michaud) |
| **Final Fund Portfolio** | **Реальная композиция фонда** (BL → caps → CVaR-Defense) |

#### 4.2.3 Сравнительная таблица

Под карточками — широкая таблица «Strategy Comparison». В одной строке — все метрики:

| Колонка | Что значит |
|---|---|
| `RETURN` | Годовая доходность |
| `VOL` | Годовая волатильность (σ) |
| `SHARPE` | Sharpe ratio |
| `SORTINO` | Sortino ratio |
| `MAX DD` | Максимальная историческая просадка |
| `CVAR 95%` | Средняя потеря в худшие 5% дней |
| `CVAR 99%` | Средняя потеря в худшие 1% дней |
| `CALMAR` | Return / \|Max DD\| |
| `ULCER` | Глубина + длительность просадок |
| `B-BTC` | Beta к BTC (амплитуда движений) |
| `BTC` / `ETH` / `ALTS` | Состав по группам |
| `P-BTC` | Корреляция с BTC |
| `NOTE` | Описание / алёрт о применённых caps |

**Кнопка «Copy CSV»** — экспорт таблицы в Excel/Sheets.

**Польза**:

- **Согласие между моделями = высокая уверенность.** Если 10 из 14 говорят «BTC 60-70%» — сигнал устойчивый. Разлёт от 5% до 80% — данные шумные.
- **Сравнение tail-risk**: какая модель даёт лучший CVaR, какая лучший Calmar.
- **Sanity check для Final Fund**: финальная композиция должна быть «где-то рядом» с устойчивыми моделями (HRP, MaxDiv), а не копировать Max Sharpe.

**Когда смотреть**: каждый раз перед Copy NAV. Понять, что фонд не оптимизирован под data-mining outliers.

### 4.3 Risk Caps & Views — policy floor

**Что это**: правила игры для оптимизатора. Это **политика управления риском** фонда — самая важная вкладка для соответствия mandate'у инвестора.

Раздел применяется к финальной композиции в порядке:

```
Black-Litterman базовые → per-asset caps → aggregate rules → CVaR-Defense → Final Fund
```

#### 4.3.1 Recommendation Mode — три preset'а

Один клик меняет все настройки под выбранный профиль.

| Mode | BTC ≤ | CVaR порог | Sleeves | Когда выбирать |
|---|---|---|---|---|
| **Conservative** | 70% | −6.0% дневной | 5% | Защитная фаза, осторожные LP |
| **Balanced** ← default | 65% | −8.0% дневной | 10% | Базовый режим |
| **Aggressive** | 55% | −10.0% дневной | 10% | Бычья фаза, искушённые LP |

`Sleeves` = bot strategies + manual book — части фонда вне спота.

#### 4.3.2 Per-Asset Caps

Индивидуальные min/max доли по каждому активу:

| Symbol | Min | Max | Логика |
|---|---|---|---|
| **BTC** | 45% | 76% | Ядро |
| **ETH** | 15% | 25% | Второе ядро |
| **SOL** | 2% | 12% | Major high-beta L1 |
| **BNB** | 2% | 5% | Exchange counterparty |
| **HYPE** | — | 5% | Свежий листинг — только cap |
| **TON** | 2% | 5% | High-beta альт |
| **OKB** | — | 3% | Exchange counterparty + регуляторный риск |

«—» в min = «нет минимального лимита». Для свежих активов это правильно.

**Это и есть та защита, благодаря которой Final Fund не имеет 73% в HYPE**, даже если Max Sharpe этого хочет.

#### 4.3.3 Aggregate Rules

- **BTC + ETH Floor: 70%** — сумма ядра не может быть меньше. Страхует от «engine ушёл в альты».
- **Small Alts Cap: 10%** — сумма всех мелких альтов ≤ 10%. Предотвращает накопление 7×5% позиций.

#### 4.3.4 CVaR-Defense порог

> Если CVaR-95 итогового портфеля **хуже −8.0% дневной**, система автоматически добавит +10% веса к BTC/ETH из non-core активов.

Это последний рубеж после всех caps. Срабатывает при корреляционных хвостах — когда даже capped композиция оказывается слишком хрупкой.

#### 4.3.5 Black-Litterman Views (ниже на странице)

Твои **субъективные ожидания** по активам:

```
BTC:  expectedReturn=20%, confidence=80%, maxWeight=65%
ETH:  expectedReturn=15%, confidence=80%, maxWeight=25%
SOL:  expectedReturn=40%, confidence=60%, maxWeight=12%
...
```

Black-Litterman берёт equilibrium-prior (рыночные веса) и **байесовски смешивает с твоим view**. Чем выше confidence — тем сильнее tilt в сторону view.

**Польза**: гибкий механизм. Не «дай SOL 12%», а «жду 40% доходности с уверенностью 60%» — engine посчитает оптимальный вес.

**Кнопка «Reset to defaults»** — сброс к Balanced.

### 4.4 Stress Test — что-если сценарии

**Что это**: проверка устойчивости портфеля к **резким шокам**.

Состоит из двух частей:

#### 4.4.1 Историческая хвостовая статистика

Карточки с метриками выбранной стратегии:

- **CVaR-95** и **CVaR-99** — средняя потеря в худшие 5% и 1% дней.
- **Худший день** — самая большая дневная просадка за бэктест.
- **Max DD** — максимальная пиковая просадка.

#### 4.4.2 Канонические сценарии шока

Три заранее заданных сценария + кастомный:

| Сценарий | BTC | ETH | Альты | Аналог в истории |
|---|---|---|---|---|
| **Moderate bear** | −20% | −25% | −35..40% | Q1-2022 |
| **Severe drawdown** | −40% | −50% | −60..70% | Март 2020 / FTX-неделя |
| **Idiosyncratic shock** | −10% | −15% | −50% на 1-2 активах | Терра, USDC де-пеггинг |
| **Custom** | задаёшь сам | | | сценарий для пресентаций инвесторам |

Для каждого считается:

- **Portfolio loss** — общая потеря в день шока.
- **Top contributor** — какой актив дал самый большой вклад в потерю.
- **Бар-чарт** — разложение CVaR-95 по активам (кто исторически больше всех «болит»).

**Польза**:

- Понимаешь **где портфель хрупкий**. Если 60% потерь приходят от одного актива — это концентрационный риск.
- **Готовишь стресс-отчёт инвесторам**: «если случится Терра-style событие, фонд потеряет X%». Они любят такие цифры.
- **Сравниваешь модели по устойчивости**: Final Fund vs Max Sharpe — кто переживёт хуже?

**Когда смотреть**: после Recommended Tab, перед Copy NAV — убедиться, что финальная композиция не рассыпется в crash.

### 4.5 Recommended — финальный портфель фонда

**Это центральная вкладка платформы.** Здесь живёт **Final Fund Portfolio** и всё, что нужно оператору для принятия решения о ребалансе.

Идёт сверху вниз в логическом порядке:

#### 4.5.1 Confidence badge

Триаж-оценка от 0 до 100% по 8 факторам (data quality, model agreement, liquidity, momentum, и др.). Уровни:

- **🟢 High** (≥ 70) — модели согласны, данные качественные, фонд устойчив. Можно публиковать NAV.
- **🟡 Medium** (40-70) — есть напряжения, но действовать можно. Прочитай Why narrative внимательнее.
- **🔴 Low** (< 40) — серьёзные проблемы (короткая история, ликвидность, расхождение моделей). **Не публикуй NAV без ревью**.

#### 4.5.2 Vol Target advisory

Рекомендация по cash-buffer'у на основе текущей реализованной волатильности фонда. Например: «фонд имеет σ=55%, целевая σ=45%, рекомендуется добавить 15% USDT-cash в sleeve».

#### 4.5.3 Why narrative

5-параграфный текст, **объясняющий почему такая композиция**. Включает:

- Какие активы дают вклад в Sharpe.
- Какие caps сработали.
- Какие views оператора были учтены.
- Почему CVaR-Defense сработал или нет.
- Какие альтернативные модели сказали бы по-другому.

**Польза**: это **готовый текст для отчёта инвесторам**. Можно копировать.

#### 4.5.4 Spot vs Total Fund donuts

Две диаграммы рядом:

- **«Раскладка спот-куска»** — веса криптоактивов **внутри** спот-части (сумма = 100% внутри спота).
- **«Полный портфель фонда»** — те же позиции с учётом sleeves (80% спот × состав + 10% bot + 10% manual = 100% фонда).

Эти две диаграммы — **самый понятный визуал для инвестора**: «вот куда идут деньги».

#### 4.5.5 Cluster Exposure

Распределение по семи кластерам (Core, Infra, High-beta L1, Exchange, Alpha, Meme, Other) с soft-ceilings. Показывает, нет ли overexposure к одному сектору.

#### 4.5.6 Δ vs Live Fund (если задан `PIFAGOR_FUND_API_URL`)

**Сравнение target (что engine рекомендует) vs live (что в фонде сейчас)**. Таблица:

```
Symbol  Target  Live    Δ       Action
BTC     67%     65%     +2pp    BUY    ← нужно докупить
ETH     18%     20%     -2pp    SELL   ← немного продать
SOL      8%     8.1%    -0.1pp  HOLD   ← в band ±1pp
```

Кнопка **«Import current»** автозаполняет Rebalance Plan живыми весами.

**Польза**: ты сразу видишь, насколько фонд отстал от рекомендации, и можешь принять решение «ребалансим или ещё подождём».

#### 4.5.7 Rebalance Plan

Конкретный план действий для оператора:

- Заводишь текущие веса (или импортируешь из Live Fund).
- Engine считает delta vs target.
- Каждая позиция классифицируется: **BUY / SELL / HOLD / WATCH ONLY**.
- Приоритет: **High / Medium / Low** по абсолютной величине delta.

**Польза**: это **готовый to-do list** для управляющего на эту неделю.

#### 4.5.8 Rotation Suggestions

Стратегические тикеты на ротацию из 4 источников:

- **Data quality**: «У актива X короткая история — снизить с 5% до 2%».
- **Cluster overshoot**: «Cluster Alpha превысил ceiling 8% — урезать».
- **Liquidity tier**: «Актив в red tier (< $10M ADV) — снизить до 2%».
- **Core deficit**: «BTC+ETH ниже floor 70% — добавить».

#### 4.5.9 Watchlist

Активы, которые **отслеживаются, но не в портфеле** (вес ≈ 0). Делятся на:

- **No-data**: история < 90 дней, ждём.
- **Uncategorized**: не в cluster taxonomy.
- **Effectively-zero**: формально в universe, но 0%.
- **Honorary**: tracked для контекста (XRP, ADA, AVAX).

#### 4.5.10 Liquidity Layer

Оценка глубины рынка по каждому активу:

- **Avg daily USD volume** (30-дневное среднее).
- **Tier**: blue (≥$1B), green ($100M-$1B), yellow ($10M-$100M), red (< $10M).
- **Max executable ticket** (5% от ADV) — сколько можно купить, не двигая цену.
- **Basket score 0-100** — агрегированная оценка ликвидности всей корзины.

**Польза**: понять, **может ли фонд исполнить ребаланс**. Если 30% портфеля в активах с тонкой ликвидностью — придётся разбивать ордера на TWAP.

#### 4.5.11 Model Contribution

Рейтинг 14 моделей по влиянию на финальную композицию:

```
1. Black-Litterman    influence 89%
2. HRP                influence 76%
3. Min Vol            influence 64%
...
```

Чем выше influence — тем ближе модель к финальному результату. **Аудит**: какая модель «победила» в итоге.

#### 4.5.12 Backtested equity curve

Кривая капитала, как если бы держали финальные веса весь period. **In-sample** (статичные веса) — не путать с walk-forward ниже.

#### 4.5.13 Walk-forward equity

**HRP retraining out-of-sample**: каждые N дней модель перетренировывается на расширяющемся окне, веса меняются. Это **самая честная оценка** «работает ли подход». Сравнивай с in-sample кривой — если walk-forward сильно ниже, значит модель overfit.

### 4.6 Journal — audit trail

**Что это**: история всех расчётов с метаданными.

Каждая строка — один run:

```
2026-05-20 11:23 UTC  [BALANCED]  ✓ PUBLISHED  hash 270c5370  conf 60%  live-mcaps
BTC 71.3%  ETH 14.1%  HYPE 4.7%  TON 4.7%  SOL 1.9%  BNB 1.9%  OKB 1.4%
```

Что значат поля:

- **Дата + время UTC** — когда расчёт был сделан.
- **Mode badge** — какой режим был активен (Conservative/Balanced/Aggressive).
- **Published badge** ✓ — нажимал ли Copy NAV (значит ушло в фонд).
- **Hash** — детерминированный SHA-256 параметров (assets, caps, views, mode). Одинаковый hash = одинаковые параметры.
- **Conf** — Confidence score на момент расчёта.
- **`live-mcaps`** — был ли использован live market cap snapshot (vs hard-coded).
- **Веса** — все активы ≥ 0.1%.

#### 4.6.1 Действия над run'ом

- **Add note** — inline-комментарий (до 500 символов). Например: «ребаланс после Q1 отчёта, увеличили HYPE по решению комитета».
- **Compare** — выбрать два run'а и увидеть **diff весов** по каждому активу:

```
Compare:  2026-04-20  →  2026-05-20

Symbol    Before    After     Δpp
BTC       72.0%     71.3%    -0.7pp
ETH       13.5%     14.1%    +0.6pp
HYPE       3.0%      4.7%    +1.7pp
TON        5.0%      4.7%    -0.3pp
...
```

#### 4.6.2 Хранение

- **localStorage** — мгновенный доступ, до 50 последних run'ов.
- **Server disk** — durable, до 200 run'ов, переживает чистку браузера.

#### 4.6.3 Польза

1. **Аудит для комитета и LP**: «вот лог всех решений по композиции за последний год, с параметрами и обоснованием».
2. **Ретроспектива**: «3 месяца назад мы рекомендовали 67% BTC, сейчас 71%. Что изменилось?» → Compare за 1 клик.
3. **Воспроизводимость**: paramsHash гарантирует, что если ты повторишь расчёт с теми же параметрами через год — получишь те же веса (на той же data).
4. **Защита от ошибок памяти**: «Я уже делал ребаланс на этой неделе?» — открой Journal.

## 6. FAQ — типичные ситуации

### Q: Confidence низкий (< 40), что делать?

**A:** Не публикуй NAV. Прочитай разбор факторов в Confidence badge — обычно проблема в одном из трёх:

1. **Короткая история активов**: HYPE с 365 дней при 3-летнем окне. → Используй 2-летний период.
2. **Расхождение моделей**: модели сильно спорят. → Проверь, нет ли в universe актива с экстремальным историческим return (data-mining attractor).
3. **Тонкая ликвидность**: basket score < 50. → Уменьши вес активов в red tier через Risk Caps.

### Q: Δ vs Live Fund показывает большой Δ (>10pp по нескольким позициям)

**A:** Это нормально, если ребаланс делается редко. Используй Rebalance Plan для составления плана сделок. Не пытайся переторговать за один день — TWAP несколько дней.

### Q: Max Sharpe ставит 73% в HYPE, это нормально?

**A:** В Strategies tab — да, Max Sharpe всегда «жадный». В Final Fund — **никогда не должно быть**, потому что HYPE max cap = 5%. Если в Final Fund видишь HYPE > 5% — баг, репорти.

### Q: Я добавил новый актив, не в whitelist Криптофонда. Что делает Copy NAV?

**A:** Игнорирует. Warning «Не экспортированы (нет в whitelist фонда): X». Сначала нужно добавить ассет в `SUPPORTED_SPOT_SYMBOLS` на стороне Криптофонда (это уже задача backend-команды).

### Q: Где хранится Journal? Если очищу localStorage, потеряю историю?

**A:** Не потеряешь. Все published run'ы дублируются на сервер (.cache-disk на Render persistent disk). LocalStorage — это быстрый кеш для UI. После очистки браузера Journal восстановит данные с сервера при следующем заходе.

### Q: Что значит paramsHash? Зачем он нужен?

**A:** SHA-256 от всех параметров расчёта (assets + caps + views + mode + …). Если две записи в Journal имеют одинаковый paramsHash — значит расчёт сделан **с теми же настройками**. Веса всё ещё могут отличаться (потому что данные обновились), но это **тот же режим работы**. Полезно для:

- «Я делал ребаланс с этими настройками 2 недели назад?» → ищи paramsHash.
- Аудит: «комитет утвердил такой режим работы 1 января» → его paramsHash зафиксирован.

### Q: Можно ли сделать что-то backtested без публикации в фонд?

**A:** Конечно. Просто не нажимай Copy NAV. Все расчёты остаются в Journal с пометкой **без published**. Можно сравнить два неопубликованных run'а через Compare.

### Q: Почему два периода истории дают разные результаты?

**A:** Из-за разных данных в окне. На 5 годах включён медвежий рынок 2021-2022, статистика портфеля «помнит» эту просадку, модели становятся консервативнее. На 1 году — только последний год, более оптимистично. Выбор периода — это **редакторское решение** управляющего: какая часть истории сейчас репрезентативнее для будущего.

### Q: Render redeploy идёт 2 минуты, фонд тем временем недоступен?

**A:** Только research-tool недоступен 2 минуты. **Криптофонд это отдельный сервис, на него redeploy не влияет.** Инвесторы видят NAV из фонда независимо от research-tool.

## 7. Глоссарий — финансовые термины

| Термин | Что значит | Где встречается |
|---|---|---|
| **MPT** | Modern Portfolio Theory, Markowitz 1952 | Simulation tab |
| **Sharpe ratio** | (return − rf) / vol — risk-adjusted return | Везде |
| **Sortino ratio** | (return − rf) / downside_vol — штрафует только просадки | Везде |
| **Efficient Frontier** | Граница Pareto-оптимальных портфелей | Simulation tab |
| **VaR** (Value at Risk) | «90% дней потеряем не больше X%» | Risk policy |
| **CVaR** (Conditional VaR) | Средняя потеря в худшие X% дней | Stress Test, Risk Caps |
| **Max DD** | Максимальная просадка от пика до дна | Strategies, Stress |
| **Beta (β)** | Чувствительность актива к benchmark (BTC) | Strategy table |
| **Correlation (ρ)** | Связанность движений с benchmark | Strategy table |
| **Calmar ratio** | return / \|Max DD\| | Strategy table |
| **Ulcer index** | Глубина + длительность просадок | Strategy table |
| **HRP** | Hierarchical Risk Parity (López de Prado 2016) | Strategies, walk-forward |
| **Black-Litterman** | Bayesian комбинация equilibrium + views | Strategies, Views |
| **Kelly criterion** | Оптимальная доля на актив для long-term growth | Strategies |
| **Bootstrap / Resampling** | Усреднение по синтетическим выборкам | Resampled Markowitz |
| **CVaR-Defense** | Автоматическая защита: +10% в BTC/ETH при глубоком CVaR | Risk Caps |
| **Sleeves** | Доли фонда вне спот-крипты (bot + manual) | Risk Caps, Donuts |
| **Equilibrium prior** | Базовые веса по market cap (отправная точка BL) | Black-Litterman |
| **View** | Субъективное ожидание управляющего по активу | Views |
| **NAV** | Net Asset Value — стоимость одного пая фонда | Криптофонд |
| **AUM** | Assets Under Management — общий капитал фонда | Криптофонд |
| **TWAP** | Time-Weighted Average Price — исполнение ордера равномерно | Liquidity context |
| **ADV** | Average Daily Volume — средний дневной объём | Liquidity Layer |
